## 1 产品定位

OpenOctopus 是一个**命令行研发流程编排工具**，通过 YAML 配置将文档设计、代码实现、代码审查、测试验证等研发环节串联成可自动执行的工作流，解决研发人员在多个 AI 会话间手动切换的痛点。

### 1.1 核心价值

| 价值           | 说明                               |
| -------------- | ---------------------------------- |
| **流程自动化** | 将"人肉编排"转变为"自动驱动"       |
| **状态可追溯** | 执行结果、中间产物、决策依据全记录 |
| **人机协作**   | 支持自动执行与人工介入的灵活切换   |
| **可复用性**   | YAML 配置驱动，团队共享最佳实践    |

### 1.2 目标用户

- 使用 Claude Code / Codex 进行日常开发的研发人员
- 需要规范研发流程的技术团队

## 2 核心理念

OpenOctopus 的核心不是“多 Agent 本身”，而是“**基于文件系统的可追溯协作总线**”。

### 2.1 单一事实源：Markdown 文件

- 会话状态、调度计划、角色结论、执行时间线全部落在 `.octopus/sessions/{session_id}/` 下的 `.md` 文件。
- 不依赖数据库作为主状态源；内存态只是运行缓存，重启后可由文件完全恢复。
- 每个关键步骤都必须有对应文件记录，保证复盘、审计、回放可执行。

### 2.2 主 Agent 决策原则

- 用户默认只和主 Agent 对话；所有自然语言输入、追问、驳回、补充约束先追加写入 `planner/human_messages.md`。
- 主 Agent 消费 `human_messages.md` 后，负责更新 `planner/requirement.snapshot.md`、`planner/master_schedule.md` 和目标角色 `context.md/inbox.md`。
- 子 Agent 不直接读取用户输入，不依赖临时聊天上下文；每一轮都由运行时强制先读 `context.md`、`inbox.md` 与最近的 `turns/*-input.md` 再执行。
- 主 Agent 只基于文件做决策，不基于临时上下文做隐式判断。
- 主决策输入固定为：
  - `planner/human_messages.md`
  - `planner/requirement.snapshot.md`
  - 各子 Agent 的 `roles/{role_id}/conclusion.md`
  - 主控排程 `planner/master_schedule.md`
  - `bus/interrupts.md`
- 主 Agent 负责任务拆分、路由、人工输入吸收、回流和终态判定；子 Agent 只负责按角色执行并产出结论文件。

### 2.3 协作机制：文件即协议

- `inbox.md` / `outbox.md`：任务分发与回执。
- `context.md`：主 Agent 物化给角色的执行上下文，子 Agent 每轮强制先读。
- `human_messages.md`：人工输入唯一入口，主 Agent 消费并转译为任务变化。
- `lock.md`：并发调度锁，避免多写冲突。
- `events.md`：先写事件，再推进状态（WAL 思想）。
- `offsets.md`：角色消费位点与被动触发依据。
- `heartbeat.md`：角色存活探测与超时处理依据。

### 2.4 设计目标

1. **稳定协作**：主 Agent 与多个子 Agent 并行时不乱序、不覆盖。
2. **可中断恢复**：任意阶段可打断、可重排、可续跑。
3. **全过程可追溯**：每次拆分、每次回合、每次决策都有文件证据链。
4. **实现简洁**：优先文件系统原语，避免过度工程化。

## 3 核心概念

### 3.1 术语定义

| 术语           | 定义                                                |
| -------------- | --------------------------------------------------- |
| **Workflow**   | 完整的研发流程定义，由多个 Stage 组成               |
| **Stage**      | 流程阶段，对应具体研发环节（如代码实现、审查）      |
| **Role**       | 执行 Stage 的角色，包含系统提示词、工具集、LLM 配置 |
| **Context**    | 跨 Stage 传递的上下文，包含中间产物、决策记录       |
| **Transition** | Stage 间流转规则，支持条件分支和循环                |
| **Artifact**   | 流程产物（文档、代码、报告等）                      |
| **Session**    | 一次具体的流程执行实例                              |

## 4 CLI 命令集

```bash
# 工作流生命周期
openoctopus init --template <name>          # 初始化工作流配置
openoctopus run [--config ./octopus.yaml]   # 执行工作流
openoctopus status [--session <id>]         # 查看状态
openoctopus resume --session <id>           # 恢复执行
openoctopus stop --session <id>             # 停止工作流
openoctopus validate --config ./octopus.yaml # 配置静态校验

# 人工介入与会话控制
openoctopus interrupt --session <id> --role <role_id> --reason "..."      # 中断指定角色
openoctopus interrupt-all --session <id> --reason "..."                    # 中断全部角色并等待人工
openoctopus inject --session <id> [--role <role_id>] --input ./note.md      # 追加人工输入
openoctopus reroute --session <id> --from <stage> --to <stage>              # 重排流转
openoctopus reset-session --session <id> --role <role_id>                   # 重置指定角色会话

# 辅助命令
openoctopus report --session <id>           # 生成执行报告
openoctopus switch --role <role_id>         # 切换 TMUX 角色会话
openoctopus debug --session <id>            # 调试模式
```

## 5 YAML 配置规范

### 5.1 完整配置示例

```yaml
version: "2.1"

meta:
  workflow_id: "feature-dev-loop"
  name: "功能开发闭环流程"
  owner: "team-openoctopus"

runtime:
  workspace:
    root: ".octopus"
    sessions_dir: ".octopus/sessions"
    artifacts_dir: ".octopus/artifacts"
    logs_dir: ".octopus/logs"
  tmux:
    enabled: true
    socket_name: "octopus-{session_id}"
    main_pane_ratio: 0.5
    role_layout: "adaptive_grid" # adaptive_grid | tiled
  checkpoint:
    enabled: true
    on_stage_boundary: true
    every_n_events: 20
  recovery:
    replay_order:
      ["bus/events.md", "state/checkpoints", "planner/master_schedule.md"]
    strict_mode: true # 丢关键文件直接失败，避免脏恢复
  scheduler:
    max_parallel_roles: 4
    dispatch_strategy: "priority_then_dependency"
  role_runtime:
    trigger_mode: "fs_event_then_poll"
    idle_poll_seconds: 2
    bootstrap_read_order:
      - "planner/requirement.snapshot.md"
      - "roles/{role_id}/context.md"
      - "roles/{role_id}/inbox.md"
    safe_interrupt_boundary: "tool_call_or_turn_end"
  human_io:
    main_agent_only: true
    conversation_file: "planner/human_messages.md"
    merge_strategy: "append_then_snapshot"
  master_watch:
    enabled: true
    progress_file: "planner/global_progress.md"
    blocker_file: "planner/blockers.md"
    auto_interrupt_all_on_deadlock: true
    max_no_progress_rounds: 3

llm_profiles:
  claude_code_cli:
    provider: "claude_code"
    mode: "cli"
    cli_path: "claude"
    max_tokens: 4096
    temperature: 0.2
  codex_cli:
    provider: "codex"
    mode: "cli"
    cli_path: "codex"
    max_tokens: 4096
    temperature: 0.1

tool_registry:
  builtin:
    file_read: { module: "openoctopus.tools.file", class: "FileReadTool" }
    file_write: { module: "openoctopus.tools.file", class: "FileWriteTool" }
    shell_exec: { module: "openoctopus.tools.shell", class: "ShellTool" }
    git_operation: { module: "openoctopus.tools.git", class: "GitTool" }
    web_search: { module: "openoctopus.tools.web", class: "WebSearchTool" }
  mcp:
    slack:
      command: "npx"
      args: ["-y", "@modelcontextprotocol/server-slack"]
      env:
        SLACK_BOT_TOKEN: "${SLACK_BOT_TOKEN}"

security:
  shell:
    allowlist_prefixes:
      ["git status", "git diff", "pytest", "npm test", "pnpm test"]
    denylist_keywords: ["rm -rf /", "shutdown", "reboot"]
  path:
    writable_roots: ["./", ".octopus/"]
    read_only_roots: ["/etc", "/var", "/usr"]

policies:
  retry:
    max_retry_per_stage: 2
    backoff_seconds: [5, 20]
  timeout:
    stage_timeout_seconds: 1800
    role_heartbeat_timeout_seconds: 120
  loop_guard:
    max_rounds_per_task: 6
    min_quality_gain: 0.05
  human_gate:
    on_high_risk: true
    high_risk_threshold: 0.8
    write_manual_input_to_markdown: true
    main_agent_ack_required: true
  session_reset:
    enabled: true
    preserve_files: true
    keep_turn_history: true
  review:
    require_design_approval: true
    require_code_doc_diff: true
  artifact:
    hash_algo: "sha256"
    keep_latest_versions: 5
  immutable_artifacts:
    paths:
      - "artifacts/{session_id}/tests/e2e/**"
    allow_writers: ["agent_c"]
  deadlock_guard:
    enabled: true
    max_no_progress_rounds: 3
    blocked_statuses: ["BLOCKED", "INTERRUPTED_PENDING_ACK"]
    on_trigger: "interrupt_all_and_wait_human"

roles:
  - id: "agent_a"
    name: "方案与实现 Agent"
    type: "react"
    llm_profile: "claude_code_cli"
    react_config:
      max_iterations: 10
    system_prompt: |
      你先负责方案设计，设计通过后重置会话，再基于批准文档实现代码、执行 E2E，并根据审核意见与测试失败自动修复。
    reset_prompt: |
      你当前已进入新会话，只保留文件系统中的批准文档、审查意见、测试结果和任务上下文，不继承旧聊天记忆。
    constraints:
      must_read_files: ["roles/{role_id}/context.md", "roles/{role_id}/inbox.md"]
      forbidden_writes: ["artifacts/{session_id}/tests/e2e/**"]
    tools: ["file_read", "file_write", "shell_exec", "git_operation", "web_search"]

  - id: "agent_b"
    name: "审核 Agent"
    type: "react"
    llm_profile: "codex_cli"
    react_config:
      max_iterations: 10
    system_prompt: |
      你负责审核设计方案，以及审核代码与文档的一致性，输出明确、可执行的审查意见。
    constraints:
      review_targets: ["design", "code_doc_diff"]
    tools: ["file_read", "file_write", "git_operation"]

  - id: "agent_c"
    name: "E2E 编写 Agent"
    type: "react"
    llm_profile: "claude_code_cli"
    react_config:
      max_iterations: 8
    system_prompt: |
      你只负责根据批准文档编写 E2E 测试；测试一旦交付，在当前验证回路中不允许被其他角色修改。
    constraints:
      emit_read_only_artifacts: ["artifacts/{session_id}/tests/e2e/**"]
    tools: ["file_read", "file_write", "shell_exec"]

stages:
  - id: "design_solution"
    name: "方案设计"
    role: "agent_a"
    input:
      - type: "requirement_file"
        path: "./docs/feature.md"
      - type: "user_prompt"
        optional: true
    output:
      - type: "artifact"
        name: "solution_doc"

  - id: "design_review"
    name: "方案审核"
    role: "agent_b"
    input:
      - type: "artifact"
        ref: "solution_doc"
    output:
      - type: "artifact"
        name: "design_review_report"

  - id: "reset_agent_a_session"
    name: "A 会话重置"
    role: "agent_a"
    mode: "session_reset"
    reset_session:
      clear_cli_context: true
      preserve_files: true
      keep_turn_history: true
      reset_reason: "design_approved_enter_implementation"
    input:
      - type: "artifact"
        ref: "design_review_report"
    output:
      - type: "artifact"
        name: "agent_a_reset_receipt"

  - id: "code_implementation"
    name: "文档驱动实现"
    role: "agent_a"
    input:
      - type: "artifact"
        ref: "solution_doc"
      - type: "artifact"
        ref: "agent_a_reset_receipt"
    output:
      - type: "artifact"
        name: "candidate_code"

  - id: "code_doc_review"
    name: "代码文档差异审核"
    role: "agent_b"
    input:
      - type: "artifact"
        ref: "candidate_code"
      - type: "artifact"
        ref: "solution_doc"
    output:
      - type: "artifact"
        name: "code_doc_review_report"

  - id: "review_fix"
    name: "按审核意见修复"
    role: "agent_a"
    input:
      - type: "artifact"
        ref: "candidate_code"
      - type: "artifact"
        ref: "code_doc_review_report"
    output:
      - type: "artifact"
        name: "candidate_code"

  - id: "e2e_authoring"
    name: "E2E 编写"
    role: "agent_c"
    input:
      - type: "artifact"
        ref: "solution_doc"
    output:
      - type: "artifact"
        name: "e2e_suite"

  - id: "e2e_execution"
    name: "E2E 执行"
    role: "agent_a"
    input:
      - type: "artifact"
        ref: "candidate_code"
      - type: "artifact"
        ref: "e2e_suite"
        access: "read_only"
    output:
      - type: "artifact"
        name: "e2e_report"

  - id: "e2e_fix"
    name: "按 E2E 失败修复"
    role: "agent_a"
    input:
      - type: "artifact"
        ref: "candidate_code"
      - type: "artifact"
        ref: "e2e_report"
      - type: "artifact"
        ref: "e2e_suite"
        access: "read_only"
    output:
      - type: "artifact"
        name: "candidate_code"

transitions:
  - from: "design_solution"
    to: "design_review"

  - from: "design_review"
    condition:
      type: "expression"
      expr: "artifacts.design_review_report.approved == true"
    on_true: "reset_agent_a_session"
    on_false: "design_solution"

  - from: "reset_agent_a_session"
    to: "code_implementation"

  - from: "code_implementation"
    to: "code_doc_review"

  - from: "code_doc_review"
    condition:
      type: "aggregate"
      mode: "all"
      rules:
        - "artifacts.code_doc_review_report.ready_for_qa == true"
        - "artifacts.code_doc_review_report.blocking_issues == 0"
    on_true: "e2e_authoring"
    on_false: "review_fix"

  - from: "review_fix"
    to: "code_doc_review"

  - from: "e2e_authoring"
    to: "e2e_execution"

  - from: "e2e_execution"
    condition:
      type: "expression"
      expr: "artifacts.e2e_report.passed == true"
    on_true: "__END__"
    on_false: "e2e_fix"

  - from: "e2e_fix"
    to: "e2e_execution"
```

### 5.3 YAML 校验与默认策略（必须）

1. **结构校验**：`roles.id`、`stages.id` 全局唯一；`stage.role` 必须引用已定义角色。
2. **引用校验**：`input.ref` 必须指向已产出的 artifact，禁止悬空引用。
3. **流转校验**：`transitions.from` 必须存在，`on_true/on_false/to` 目标必须存在或为 `__END__`。
4. **环路校验**：允许业务回路，但必须受 `policies.loop_guard` 限制，避免死循环。
5. **工具校验**：角色声明的 `tools` 必须能在 `tool_registry` 中解析。
6. **安全校验**：启用 `shell_exec` 的角色必须存在 `security.shell` 配置。
7. **默认值策略**：未配置 `retry/timeout/checkpoint` 时使用系统默认保守值，并记录到启动日志。
8. **阻断规则**：校验失败时禁止 `run`；`validate` 仅输出错误并返回非 0 退出码。
9. **会话重置校验**：`mode: session_reset` 的阶段必须绑定已存在角色，且必须声明 `clear_cli_context` 与保留策略。
10. **只读产物校验**：`immutable_artifacts.paths` 不能与未授权角色的可写路径重叠；如 `e2e_suite` 标记为 `read_only`，非授权角色不得输出到同一路径。
11. **提示词与约束校验**：每个角色允许自定义 `system_prompt`、`reset_prompt`、`constraints`，但必须能序列化为 Markdown 并被运行时解析。
12. **监控策略校验**：`master_watch`、`deadlock_guard`、`loop_guard` 的阈值必须为正数，且 `on_trigger` 必须是受支持动作。

### 5.4 YAML 规则文档（供 AI 自动生成配置）

YAML 由 **config 模块** 负责，且 config 模块除了负责解析、校验、默认值注入之外，还必须维护一份给 AI 使用的 Markdown 规则文档，建议路径为 `docs/config/001/yaml-rules.md`。

这份 Markdown 不是普通说明文档，而是 OpenOctopus 的“**配置生成协议**”。后续应支持让 AI 先读取这份规则文档，再自动生成 `octopus.yaml`，最后由 `openoctopus validate/run` 直接消费执行。

规则文档至少包含以下内容：

1. **结构规则**：顶层字段、嵌套对象、必填项、默认值、引用关系。
2. **角色规则**：每个 agent 可配置的 `system_prompt`、`reset_prompt`、`constraints`、工具权限、可读写边界。
3. **流程规则**：`stages`、`transitions`、回路、`session_reset`、`interrupt-all`、`deadlock_guard` 的合法写法。
4. **约束规则**：如 `immutable_artifacts`、只读输入、E2E 不可修改、某角色只能审查不能落码等典型限制。
5. **坑点清单**：循环依赖、引用悬空、只读路径冲突、角色权限过宽、会话重置后遗漏上下文、Master 监控阈值过小等问题。
6. **可复制示例**：至少提供 A/B/C + Master 理想自动化模板、单 Agent 极简模板、带人工打断模板三个例子。

约束要求：

- 规则文档与 config 模块的真实校验逻辑必须同步维护，不能出现“文档允许但运行时报错”的分叉。
- 运行时报错要能回溯到规则文档中的具体条目，便于 AI 自动纠正 YAML。
- 任何新增 YAML 能力，都必须先补规则文档，再开放给运行时使用。

## 6 TMUX 编排与运行视图

### 6.1 指定 YAML 后的启动时序

最终运行入口统一为：

```bash
openoctopus run --config ./octopus.yaml --requirement ./docs/feature.md
```

系统固定按以下步骤执行：

```text
[读取 YAML 配置]
        |
        v
[校验 roles/stages/transitions]
        |
        v
[创建 session_id 与工作目录]
        |
        v
[启动 tmux server: octopus-{session_id}]
        |
        v
[构建主控+角色窗格布局]
        |
        v

        |
        v

        |

        |
        v
[role runtime 监听 md 变更并被动触发子 Agent]
        |
        v
[汇总结果/打断处理/人工输入回流/归档]
```

### 6.2 固定布局：左主右子（自动横竖拆分）

布局规则：

1. 整体窗口先做一次水平分割，左 50% 固定给主 Agent（主会话）。
2. 右 50% 作为角色区，根据 `roles` 数量自动拆分多个 pane。
3. 右侧拆分策略采用“近似网格”：
   - 角色数 1：右侧单 pane。
   - 角色数 2：上下二分（垂直拆分）。
   - 角色数 3-4：先上下，再左右，形成 2x2。
   - 角色数 >4：继续按 `tiled` 扩展，保持可读性。

示意（4 个角色）：

```
┌──────────────────────────────┬──────────────────────────────┐
│            主 Agent          │          角色A 对话          │
│ 需求拆分 / 调度 / 决策 /总线 │──────────────────────────────│
│                              │          角色B 对话          │
│                              ├──────────────────────────────┤
│                              │          角色C 对话          │
│                              │──────────────────────────────│
│                              │          角色D 对话          │
└──────────────────────────────┴──────────────────────────────┘
```

### 6.3 主 Agent 与子 Agent 的 Pane 责任

| 区域          | 责任                                         | 输入                                   | 输出                                               |
| ------------- | -------------------------------------------- | -------------------------------------- | -------------------------------------------------- |
| 左侧主 Pane   | 全局规划、任务拆分、调度、结果验收、回路控制 | 用户需求、`planner/human_messages.md`、YAML、各角色 `conclusion.md` | `requirement.snapshot.md`、`master_schedule.md`、`context.md/inbox.md`、阶段判定 |
| 右侧角色 Pane | 按角色定位执行子任务（实现/测试/e2e/审查等） | `context.md`、`inbox.md`、最新回合输入、打断/补充事件 | `conclusion.md`、回合产物、状态更新、异常/打断事件 |

### 6.4 人工打断与动态更新

系统支持在执行中对任意子 Agent 发起打断或更新，但所有人工动作都必须先落 Markdown，再由主 Agent 感知并重编排：

- `openoctopus interrupt --session <id> --role <role_id> --reason "..."`  
  立即写入 `bus/events.md` 与 `bus/interrupts.md`，标记角色进入 `INTERRUPTED_PENDING_ACK`，角色运行时在安全边界停下。
- `openoctopus interrupt-all --session <id> --reason "..."`  
  由主 Agent 或守护器批量中断全部角色，写入 `planner/global_progress.md` 与 `planner/blockers.md`，并将会话置为 `WAITING_HUMAN`。
- `openoctopus inject --session <id> --role <role_id> --input ./patch.md`  
  先将人工补充内容追加到 `planner/human_messages.md`，再由主 Agent 合并到 `planner/requirement.snapshot.md`，必要时重写目标角色 `context.md` 和 `inbox.md`。
- `openoctopus reroute --session <id> --from <stage> --to <stage>`  
  由主 Agent 更新 `master_schedule.md`、`decision_log.md`，并发布新的角色任务。
- `openoctopus reset-session --session <id> --role <role_id>`  
  仅重置目标角色的 CLI 会话与临时上下文，保留 Markdown 证据、产物引用和历史回合文件，并写入 `roles/{role_id}/session.reset.md`。

设计约束：

1. 用户不直接和子 Agent 建立新会话；即使指定 `--role`，也只是声明“影响目标”，真正分发仍由主 Agent 完成。
2. 所有打断、补充输入、驳回意见都要有对应 Markdown 证据，恢复时按文件可完整重放。
3. 子 Agent 在恢复或续跑前必须重新读取最新 `context.md`，不能沿用旧回合的临时上下文。

### 6.5 常用快捷键

| 操作             | 快捷键    | 说明                 |
| ---------------- | --------- | -------------------- |
| 切回主 Pane      | `C-b o`   | 快速回到左侧主控窗格 |
| 在右侧角色间切换 | `C-b ;`   | 循环切换角色窗格     |
| 角色 pane 放大   | `C-b z`   | 聚焦单个角色细看     |
| 重新平铺右侧     | `C-b M-5` | 强制重排角色区布局   |

## 7 Go 状态机总线编排引擎

### 7.1 总线化状态机实现图

```text
[START]
   |
   v
[LoadConfig] -> [InitSessionState] -> [InitTmuxLayout] -> [MainAgent.Plan]
                                                              |
                                                              v
                                                     [TaskBus.Dispatch]
                                                              |
                                                              v
                                                 [RoleAgent.Execute 并行子图]
                                                      |                |
                                                      |                +--> [InterruptHandler]
                                                      |                         |
                                                      +--> [TaskBus.Collect] <--+
                                                               |
                                                               v
                                                       [MainAgent.Evaluate]
                                                          |    |        |
                                                          |    |        +--> [HumanGate.Wait] -> [审批结果] --继续--> [MainAgent.Plan]
                                                          |    |                                         \
                                                          |    |                                          --终止--> [END]
                                                          |    |
                                                          |    +--> [继续拆分] -> [MainAgent.Plan]
                                                          |
                                                          +--> [完成] -> [END]
```

该图对应“主 Agent + 事件总线 + 多角色子图”的统一模型：

- 主 Agent 只做编排，不做具体实现细节。
- 子 Agent 只执行角色职责，通过总线回传结构化结果。
- 是否继续、回滚、重分配，统一由主 Agent 判定。

Go 版不建议继续寻找 LangGraph 的一比一替代框架。OpenOctopus 的首版核心难点不在图框架本身，而在**文件协议、状态落盘、调度收口和恢复顺序**；因此更推荐采用“自研 coordinator + 显式状态机 + Markdown/WAL 协议”的方式实现，必要时只引入轻量状态机库辅助状态迁移。

### 7.2 主图与子图关系（Go 分层编排）

```text
Main Coordinator Graph:
[需求解析] -> [任务拆分] -> [任务分配] -> [结果验收] -> [通过?]
                                                      |        |
                                                      |否      |是
                                                      v        v
                                                   [任务拆分] [归档结束]

Role Worker Subgraph:
[接收任务] -> [执行回合] -> [写 turns 与 conclusion.md] -> [回执总线]

Graph Relation:
[任务分配] ---> [接收任务]
[回执总线] ---> [结果验收]
```

### 7.3 状态模型（文件系统 + Markdown）

系统不依赖数据库做主状态，统一使用 `.md` 文件表达状态与协作协议。

**SessionContext（全局）字段**

- `session_id`: 会话标识
- `requirement_snapshot`: 当前需求快照版本
- `human_message_cursor`: 主 Agent 已消费到的人工输入位点
- `pending_manual_inputs`: 待吸收的人工增量输入
- `global_progress`: 当前全局进度摘要
- `stagnation_counter`: 无进展轮次数
- `task_board`: 主 Agent 任务看板
- `role_registry`: 角色能力映射（来自 YAML）
- `routing_table`: 任务与角色路由
- `interrupt_queue`: 打断队列
- `artifact_index`: 全局产物索引
- `decision_log`: 主 Agent 决策链

**RoleState（每角色）字段**

- `role_id` / `pane_id`: 角色与 tmux 窗格绑定
- `current_task_id`: 当前任务
- `turn`: 当前执行轮次
- `session_generation`: 当前角色会话代际
- `context_version`: 当前角色上下文版本
- `last_output_ref`: 最近回执产物
- `last_consumed_event_id`: 最近消费事件
- `stop_requested`: 是否收到打断请求
- `status`: IDLE | RUNNING | BLOCKED | INTERRUPTED | DONE

**字段落盘文件约定**

| 状态对象              | 文件路径                                                   | 写入策略               |
| --------------------- | ---------------------------------------------------------- | ---------------------- |
| SessionContext 当前态 | `.octopus/sessions/{id}/session.state.md`                  | 覆盖写（原子替换）     |
| 人机对话日志          | `.octopus/sessions/{id}/planner/human_messages.md`         | 追加写                 |
| 全局进度报告          | `.octopus/sessions/{id}/planner/global_progress.md`        | 覆盖写（原子替换）     |
| 主控排程              | `.octopus/sessions/{id}/planner/master_schedule.md`        | 局部更新（原子替换）   |
| 主任务看板            | `.octopus/sessions/{id}/planner/task_board.md`             | 局部更新（原子替换）   |
| 决策链                | `.octopus/sessions/{id}/planner/decision_log.md`           | 追加写                 |
| 角色状态              | `.octopus/sessions/{id}/roles/{role}/state.md`             | 覆盖写（原子替换）     |
| 会话重置记录          | `.octopus/sessions/{id}/roles/{role}/session.reset.md`     | 追加写                 |
| 角色上下文            | `.octopus/sessions/{id}/roles/{role}/context.md`           | 覆盖写（原子替换）     |
| 角色结论              | `.octopus/sessions/{id}/roles/{role}/conclusion.md`        | 覆盖写（保留版本快照） |
| 角色回合输入          | `.octopus/sessions/{id}/roles/{role}/turns/000N-input.md`  | 新文件                 |
| 角色回合输出          | `.octopus/sessions/{id}/roles/{role}/turns/000N-output.md` | 新文件                 |

### 7.4 循环与回路控制（主 Agent 统一收口）

典型回路：需求拆分 → 实现 → 测试/e2e → 审查 → 决策。  
主 Agent 对每一轮做三类判定：

1. **通过**：推进到下一阶段或结束。
2. **修复**：回流到实现角色，附带差异化修复指令。
3. **升级**：进入人工审批或重新拆分策略。

控制项：

- `max_rounds_per_task`: 单任务最大回合数
- `max_retry_per_role`: 角色最大重试次数
- `improvement_threshold`: 增量改善阈值（防止无效循环）
- `timeout_policy`: 超时后的自动策略（重试/暂停/终止）

### 7.5 条件流转与聚合策略

**流转条件类型：**

- `expression`: 简单布尔表达式（受限 DSL，不执行任意代码）
- `aggregate`: 多条件组合（all/any/majority）
- `role_aggregate`: 多角色结果聚合（all/any/majority）

**聚合结果字段建议：**

- `quality_score`
- `risk_level`
- `blocking_issues`
- `ready_for_merge`

## 8 事件总线与信息流转

### 8.1 核心设计原则

1. **所有状态变更必须通过事件总线** - 禁止直接修改状态
2. **事件持久化先行（WAL 模式）** - 先写 Markdown 日志，再更新内存
3. **完整的信息血缘追踪** - 产物来源、决策依据全记录
4. **断点可恢复性** - 任意时刻可重建完整状态

### 8.2 事件类型体系

```
Event Types
│
├── System Events
│   ├── WORKFLOW_INITIALIZED / STARTED / COMPLETED / FAILED
│   ├── WORKFLOW_PAUSED / RESUMED / CANCELLED
│
├── Stage Events
│   ├── STAGE_SCHEDULED / STARTED / COMPLETED / FAILED
│   ├── STAGE_RETRYING / SKIPPED / WAITING_HUMAN
│
├── Role Events
│   ├── ROLE_ASSIGNED / PROMPT_SENT / RESPONSE_RECEIVED
│   ├── ROLE_STREAM_STARTED / STREAM_CHUNK / STREAM_COMPLETED
│   ├── ROLE_TOOL_CALLED / TOOL_COMPLETED
│   ├── ROLE_TRIGGERED / ROLE_INTERRUPT_ACKED
│
├── Artifact Events
│   ├── ARTIFACT_CREATED / UPDATED / VERSIONED / PERSISTED
│
└── User Events
    ├── USER_MESSAGE_WRITTEN / USER_INTERRUPT_REQUESTED
    ├── USER_INJECTION_WRITTEN / APPROVAL_GIVEN / REJECTION_GIVEN
```

### 8.3 Markdown 多层持久化架构

```
Layer 1: Event WAL (Markdown)
├── 位置: .octopus/sessions/{session_id}/bus/events.md
├── 格式: 追加写 Markdown 条目（时间戳 + 事件ID + 类型 + 载荷 + hash）
├── 策略: 同步写入，写入成功后才允许状态推进
└── 用途: 崩溃恢复、事件回放

Layer 2: State Snapshots (Markdown)
├── 位置: .octopus/sessions/{session_id}/state/checkpoints/*.md
├── 格式: 每步一个快照文件（step-0001.md）
├── 策略: 阶段边界和回合结束触发
└── 用途: 快速恢复、定位问题

Layer 3: Role Runtime Logs (Markdown)
├── 位置: .octopus/sessions/{session_id}/roles/{role_id}/
├── 格式: state.md / context.md / turns/*.md / events.md
└── 用途: 单角色执行历史、回合审计

Layer 4: Audit & Archive (Markdown)
├── 位置: .octopus/sessions/{session_id}/audit/*.md
├── 格式: timeline.md / lineage.md / summary.md
└── 用途: 长期复盘、团队共享
```

事件条目建议格式（示例）：

```markdown
### event-000123

- ts: 2026-03-03T10:15:21Z
- event_type: ROLE_RESPONSE_RECEIVED
- session_id: sess_abc123
- role_id: impl_agent
- correlation_id: task-42-turn-03
- payload_ref: roles/impl_agent/turns/0003-output.md
- hash: sha256:8ef2...
```

### 8.4 步骤级存储机制（全过程 Markdown 落盘）

为保证主 Agent 与多个子 Agent 协作稳定，执行信息和状态全部写入 Markdown：

```
.octopus/sessions/{session_id}/
├── session.state.md                    # 全局当前状态（主 Agent 读写）
├── timeline.md                         # 全局时间线（追加写）
├── planner/
│   ├── requirement.snapshot.md         # 当前需求快照
│   ├── human_messages.md               # 用户与主 Agent 对话日志
│   ├── master_schedule.md              # 主 Agent 统筹排程（唯一调度真相）
│   ├── task_board.md                   # 任务看板：Todo/Doing/Done/Blocked
│   ├── global_progress.md              # Master 实时进度总览
│   ├── blockers.md                     # 死循环/阻塞报告与人工提示
│   ├── task_graph.mmd                  # 任务依赖图
│   ├── dispatch_log.md                 # 分发日志
│   └── decision_log.md                 # 主 Agent 决策日志
├── bus/
│   ├── events.md                       # 总线事件日志（唯一事实源）
│   ├── interrupts.md                   # 打断与注入记录
│   ├── offsets.md                      # 子 Agent 消费位点
│   └── lock.md                         # 调度锁与持有者
├── roles/
│   ├── req_split_agent/
│   │   ├── state.md                    # 当前角色状态
│   │   ├── session.reset.md            # 会话重置记录与代际
│   │   ├── context.md                  # 主 Agent 物化后的角色上下文
│   │   ├── inbox.md                    # 待处理任务（主 Agent 投递）
│   │   ├── outbox.md                   # 结果回执（子 Agent 回传）
│   │   ├── conclusion.md               # 角色最新结论（主 Agent 直接读取）
│   │   ├── heartbeat.md                # 心跳时间与存活标记
│   │   ├── events.md                   # 角色事件日志
│   │   └── turns/
│   │       ├── 0001-input.md
│   │       ├── 0001-output.md
│   │       └── ...
│   ├── impl_agent/
│   ├── test_e2e_agent/
│   └── review_agent/
├── artifacts/
│   ├── index.md                        # 产物索引
│   ├── tests/
│   │   └── e2e/                        # 只读 E2E 用例目录
│   └── {task_id}/
│       ├── result.v1.md
│       ├── result.v2.md
│       └── diff.v1-v2.md
└── audit/
    ├── lineage.md                      # 任务-角色-产物血缘
    ├── replay.md                       # 恢复与回放说明
    └── final-report.md                 # 最终报告
```

写入原则：

1. 先写 `bus/events.md`，再写对应 `state.md`（WAL 先行）。
2. 主 Agent 与子 Agent 通过 `inbox.md/outbox.md` 解耦，不共享内存。
3. 每一轮必须生成 `turns/NNNN-input.md` 与 `turns/NNNN-output.md`。
4. 主 Agent 决策只读取各角色 `conclusion.md` 与 `planner/master_schedule.md`。
5. 事件类文件（`events.md`/`decision_log.md`）采用追加写；当前态文件（`state.md`/`session.state.md`）采用原子替换写。
6. 所有覆盖写文件在落盘前先写 `*.tmp`，再 `rename` 替换，避免半写状态。
7. 所有人工输入先落 `planner/human_messages.md`；主 Agent 消费后才可更新 `requirement.snapshot.md` 与角色 `context.md/inbox.md`。
8. 子 Agent 每轮启动前必须重读 `context.md`、`inbox.md` 和最近未消费的打断事件，不能跳过文件同步。
9. Master 必须周期性重写 `planner/global_progress.md`，一旦触发死循环或阻塞判定，同步写 `planner/blockers.md` 并执行 `interrupt-all`。
10. 被声明为只读的产物（如 `artifacts/tests/e2e/**`）只能由授权角色输出，其他角色只允许读取和执行。

### 8.5 主从协作文件协议（避免并发冲突）

为保证多 Agent 并行时不乱序、不覆盖，约定如下：

1. **锁协议**：主 Agent 写 `bus/lock.md`（`holder` + `lease_token` + `lease_version` + `expire_at`），分发结束后释放。
2. **触发协议**：角色执行器通过 `bus/offsets.md` 记录消费位点，发现 `inbox.md`/`context.md` 版本变化或新的 `interrupts.md` 事件后，触发新回合或中止当前回合。
3. **领取协议**：子 Agent 从 `inbox.md` 领取任务后写 `state.md` 为 `RUNNING`。
4. **结论协议**：子 Agent 每轮必须更新 `conclusion.md`，主 Agent 仅基于该文件做阶段判定。
5. **回执协议**：子 Agent 完成后写 `outbox.md`，由主 Agent 统一消费并更新 `master_schedule.md` 与 `task_board.md`。
6. **心跳协议**：子 Agent 定期刷新 `heartbeat.md`；超时由主 Agent 触发打断或重分配。
7. **人工输入协议**：所有用户补充、驳回、改单意见统一先追加到 `planner/human_messages.md`；主 Agent 消费后才能写入角色上下文。
8. **冲突协议**：写入前校验 `lease_version`，版本不一致则拒绝写入并重试。
9. **重置协议**：`reset-session` 只清空角色 CLI 会话上下文，不删除历史 `turns/*.md`、结论文件和产物引用；必须递增 `session_generation`。
10. **只读产物协议**：标记为 `read_only` 的 artifact 只能被读取、执行或引用，不能被未授权角色覆盖写。
11. **恢复协议**：崩溃后按 `events.md -> checkpoints/*.md -> master_schedule.md` 顺序重建状态。

## 9 核心功能详细设计

### 9.1 会话生命周期

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│INITIAL  │───→│ RUNNING │───→│ WAITING │───→│ RUNNING │───→│COMPLETED│
│ 初始化  │    │ 运行中  │    │ 等待人工 │    │ 运行中  │    │ 已完成  │
└─────────┘    └────┬────┘    └────┬────┘    └─────────┘    └─────────┘
                    │              │
                    ▼              │ 用户输入
               ┌─────────┐         │
               │ FAILED  │◀────────┘
               │ 失败    │
               └─────────┘
```

**持久化时机：**

- 阶段开始/完成：保存 checkpoint
- 人工介入点：保存等待状态
- 定时触发：防止意外丢失
- 优雅停止：标记暂停状态

### 9.2 人机协作系统

| 场景     | 触发条件     | 用户操作       | 系统响应                 |
| -------- | ------------ | -------------- | ------------------------ |
| 方案确认 | 技术方案完成 | 查看/批准/驳回 | 通过则继续，驳回则重设计 |
| 代码审查 | 审查发现问题 | 查看/修复确认  | 确认后标记修复完成       |
| 测试失败 | 测试不通过   | 查看日志/决策  | 重试/跳过/中止           |
| 超时等待 | 阶段执行超时 | 确认继续/停止  | 根据选择执行             |
| 子 Agent 打断 | 子 Agent 被手动中断或主动阻塞 | 输入补充说明/指定影响角色 | 先写 `human_messages.md`，主 Agent 更新快照并重发任务 |

补充约束：用户永远面向主 Agent；即使这条人工输入最终只影响某一个子 Agent，系统也必须先写 `planner/human_messages.md`，再由主 Agent 转译成新的角色上下文与任务分发。

### 9.3 产物版本管理

**版本控制机制：**

- 自动检测同名产物，递增版本号
- 记录版本间差异（diff）
- 维护版本血缘关系（previous_version 引用）
- 产物 ID 格式：`{session_id}:{name}:v{version}`

**产物元数据：**

- 创建时间、创建者（stage/role）
- 内容指纹（hash）
- 版本差异对比
- 引用关系图谱

### 9.4 错误处理与恢复

**错误分类：**

- **ConfigError**: YAML 语法错误、必填项缺失、类型不匹配
- **ExecutionError**: LLM 调用失败、工具执行失败、超时
- **TransitionError**: 条件表达式错误、目标阶段不存在
- **SystemError**: 存储错误、网络错误、权限错误

**处理策略：**

- `retry`: 延迟后重试
- `skip`: 跳过当前阶段
- `pause`: 暂停等待人工
- `abort`: 中止工作流

### 9.5 主 Agent 实现图（任务拆分总线）

```text
[用户只与主 Agent 对话]
              |
              v
[写 planner/human_messages.md]
              |
              v
[主 Agent 合并 requirement.snapshot.md]
              |
              v
       [构建任务树 TaskTree]
              |
              v
      [按角色能力拆分子任务]
              |
              v
 [生成角色 context.md / inbox.md]
              |
              v
 [role runtime 监听 md 变化并触发子 Agent]
              |
              v
   [各角色写 conclusion.md / outbox.md]
              |
              v
[主 Agent 读取 conclusion.md + master_schedule.md + human_messages.md]
              |
              v
       [主 Agent 质量门禁评估]
              |
              v
         [是否达成目标?]
            |        |
           是        否
            |        v
            |   [问题类型?]
            |    |    |    |
            |   修复  变更  阻塞
            |    |    |    |
            |    v    v    v
            | [生成修复任务] [更新需求快照并重拆分] [触发人工介入]
            |      |               |                  |
            +------|---------------+------------------+
                   v
         [发布任务到总线 TaskBus]
```

主 Agent 的核心能力分为五层：

1. **吸收层**：读取 `human_messages.md`，将人工输入合并为最新需求快照。
2. **拆分层**：根据角色定位（需求拆分/实现/e2e/审查）生成任务包。
3. **调度层**：将任务包物化为 `context.md` 与 `inbox.md`，按优先级和依赖关系投递给子 Agent。
4. **验收层**：统一收敛结果，执行质量门禁与风险判定。
5. **演进层**：在打断、需求更新、失败重试时重建任务树。

### 9.6 子 Agent 打断与更新机制

支持两类打断：

- **主控打断**：主 Agent 根据全局风险主动中断某角色执行。
- **角色自打断**：角色发现阻塞（权限、依赖、环境）主动上报中断。

无论哪类打断，都遵守“先写 Markdown，再切换状态，再触发续跑”。

处理流程：

1. 运行时写 `bus/events.md` 与 `bus/interrupts.md`，角色 `state.md` 标记为 `INTERRUPTED_PENDING_ACK`。
2. 若用户补充说明，统一追加到 `planner/human_messages.md`；主 Agent 消费后更新 `planner/requirement.snapshot.md`。
3. 主 Agent 生成 `replan_action`（继续、换角色、降级执行、人工确认），并重写目标角色 `context.md` 与 `inbox.md`。
4. 角色运行时检测 `context_version` 或 `inbox` 序号变化后，启动下一轮或从最近 `state/checkpoints/step-XXXX.md` 续跑。
5. 子 Agent 每一轮都必须重新读取 Markdown 上下文，禁止仅依赖上次 CLI 会话里的临时内容。

### 9.7 复杂功能开发的标准角色编排模板

以“复杂功能开发需求”为例，推荐最小角色集：

- `req_split_agent`：将主需求拆成可执行子需求，输出任务树。
- `impl_agent`：实现与重构，输出代码与变更说明。
- `test_e2e_agent`：执行集成测试/e2e，输出测试报告。
- `review_agent`：执行质量审查与风险识别，输出准入结论。

主 Agent 统一把控：

- 入口需求是否可执行。
- 子任务是否覆盖完整。
- 测试与审查是否满足发布条件。
- 所有中间步骤是否已落盘可追溯。

### 9.8 E2E 真实测试体系

E2E 测试目标不是验证单个函数，而是验证 **OpenOctopus 二进制 + 本地 Docker 环境 + 文件系统总线 + TMUX/HTTP 可视界面** 组成的完整系统是否真实可运行、可恢复、可审计。

**首版原则：**

1. **真实环境优先**：必须基于本地 Docker Compose 拉起完整依赖，禁止直接 mock OpenOctopus 内部模块。
2. **黑盒验证优先**：测试入口只允许走 CLI、HTTP、浏览器与文件系统结果校验，不依赖内部私有函数。
3. **文件证据优先**：每条关键断言都应能落到 `.octopus/sessions/{id}/` 下的事件、状态、产物和审计文件。
4. **外部 LLM 受控替代**：E2E 不直接依赖线上模型供应商；测试环境通过与生产一致的 CLI/执行器适配协议接入本地 deterministic executor，保证调用路径真实、结果稳定。

**建议测试技术栈：**

- `pytest`：负责用例组织、fixture 管理、状态轮询与断言。
- `requests`：负责黑盒调用 Web 监控接口、健康检查接口和状态查询接口。
- `playwright`（Python）：负责浏览器自动化，验证监控页面、人工审批页和关键交互链路。
- `docker compose`：负责启动/停止 E2E 依赖环境，并在每次执行前做 `down -v` 清理。
- `subprocess` + `tmux capture-pane`：负责启动 `openoctopus` 命令、观察 TMUX pane 内容和验证运行期可见性。

**推荐测试路径：**

1. 清理旧环境：执行 `docker compose down -v`，删除残留 session 与 volume。
2. 构建真实二进制：编译 Go 版 `openoctopus`，通过真实命令行启动，不走库内嵌调用。
3. 准备受控测试工程：写入 `octopus.yaml`、`docs/feature.md`、测试专用执行器与固定输入产物。
4. 启动工作流：执行 `openoctopus run --config ... --requirement ...`，等待 session 初始化与事件流生成。
5. 校验主链路：断言 `events.md`、`session.state.md`、`master_schedule.md`、`conclusion.md`、`artifacts/` 等关键文件齐全且内容一致。
6. 校验交互链路：通过 Playwright 验证 Web 监控可见，通过 TMUX 捕获验证角色 pane 布局和输出，通过 CLI 校验 `status/report/resume` 命令结果。
7. 校验异常链路：构造超时、角色失败、人工打断、恢复重放等场景，验证系统能进入正确终态并留下完整证据链。

**首版 E2E 覆盖建议：**

- Happy Path：需求拆分 -> 实现 -> 测试 -> 审查 -> 完成。
- Recovery Path：运行中断后根据事件与 checkpoint 恢复继续执行。
- Human Gate Path：人工审批驳回后重新回流实现阶段。
- Failure Path：执行器超时 / 工具失败 / 写锁冲突时进入暂停、重试或失败终态。

### 10.1 故障场景与恢复

| 场景      | 检测方式 | 恢复策略                                       |
| --------- | -------- | ---------------------------------------------- |
| 进程崩溃  | 心跳超时 | 读快照 → 重放 WAL → 重建状态 → 继续执行        |

### 10.2 数据完整性校验

- **事件校验**: 签名验证
- **文件校验**: SHA256（可选 BLAKE3）
- **序列校验**: 序列号连续性
- **因果校验**: 父事件存在性

## 12 技术选型与推荐框架

Go 版建议坚持“主流程尽量标准库 + 只在边界引入轻量框架”的原则。OpenOctopus 的关键不是追求框架炫技，而是让配置、状态、总线、调度、恢复和 E2E 证据链都足够稳定。

| 技术 / 框架 | 建议用途 |
| --- | --- |
| **Go** | 作为主实现语言，交付单二进制，适合 CLI、调度器、文件 IO 和并发控制。 |
| **Cobra** | 负责 CLI 命令树、参数解析、帮助信息和 shell completion。 |
| **Koanf** | 负责 YAML / 环境变量 / flags 的分层合并，配置行为更显式，适合首版控制复杂度。 |
| **go-playground/validator** | 负责配置结构体的字段校验、必填校验和约束校验。 |
| **自研 Coordinator + 轻量状态机库** | 负责阶段流转、回路控制、人工 gate 和恢复流程；推荐直接实现编排核心，必要时只引入轻量状态机库辅助。 |
| **Bubble Tea + Lip Gloss** | 负责 `status --watch`、调试视图、人工审批页等交互式终端界面。 |
| **TMUX** | 负责多角色 pane 编排、持久会话和远程协作观察。 |
| **Chi** | 负责 Web 监控的轻量路由与中间件装配。 |
| **templ + HTMX** | 负责服务端渲染监控页与低复杂度交互，避免首版引入重前端工程。 |
| **log/slog** | 负责结构化日志，统一 CLI、服务和恢复日志格式。 |
| **pytest + Playwright（Python）** | 负责真实黑盒 E2E 测试；虽然主程序是 Go，但测试驱动保留 Python 更适合浏览器自动化与编排。 |

**框架建议说明：**

- CLI 层优先 `Cobra`，普通命令直接文本输出；只有 `watch/debug/approve` 这类长交互场景再接 `Bubble Tea`。
- 配置层优先 `Koanf + validator`，避免首版把配置管理做成隐式“魔法行为”；如果后续需要更强生态整合，可评估 `Viper`。
- 编排层不建议引入 Go 版“LangGraph 替身”；首版直接实现 coordinator，才能把文件总线、锁协议、恢复顺序和人工 gate 严格收口。
- Web 监控优先走 `Chi + templ + HTMX`，这样能保持首版交付轻量、可维护，并与真实 E2E 浏览器测试很好衔接。

## 14 模块落地影响与执行顺序

本次补强“**主 Agent 唯一人机入口 + 子 Agent 读 Markdown 被动触发 + 打断/手动输入统一回写**”后，首版落地仍建议按能力域推进，而不是按技术层切分。原因是首版核心风险依旧不在单点技术，而在配置、状态、总线、调度、角色执行、人机回流之间的协作边界是否清晰；按能力域推进更容易把协议先做稳。

### 14.1 受本次设计影响的模块清单

1. **config**：负责 YAML DSL、Schema 校验、默认值注入、每个 agent 的提示词与约束建模，并维护 `docs/config/001/yaml-rules.md` 这份给 AI 生成 YAML 用的规则文档（规则、坑点、例子、错误修正指引都由它负责）。
2. **session**：负责 session 生命周期、`.octopus/` 目录初始化、`human_messages.md` / `global_progress.md` / `blockers.md` / `session.reset.md` 等会话文件骨架，以及角色会话代际管理。
3. **event-bus**：负责 WAL、offset、锁协议、`interrupt-all`、死循环/阻塞事件、只读产物冲突事件与恢复时的回放顺序。
4. **orchestrator**：负责 Master Agent 的主循环，包括读取人工输入、生成需求快照、A/B/C 任务编排、实时进度汇总、死循环检测、自动中断全部角色并提示用户调整。
5. **role-runtime**：负责各子 Agent 的 CLI 会话生命周期、`context.md/inbox.md` 自举读取、被动触发执行、安全边界打断、会话重置，以及只读约束的本地执行拦截。
6. **artifact**：负责方案文档、代码产物、审查意见、E2E 用例和执行报告的版本化、血缘记录、只读锁定与差异追踪，尤其要保证 `e2e_suite` 这类产物可被声明为不可修改。
7. **human-gate**：负责 `interrupt` / `interrupt-all` / `inject` / `reroute` / `approval` 等人工介入协议，保证所有人工动作先写 Markdown，再进入 Master 感知链路。
8. **cli**：负责把 `run` / `validate` / `reset-session` / `interrupt-all` / `report` 等入口稳定映射为配置加载、文件写入和运行时控制，而不是直接修改内存态。
9. **recovery**：负责根据事件、快照、角色会话代际、只读锁和产物索引恢复主从协作状态，保证会话重置后仍然可回放。
10. **tmux**：负责主 Agent / 子 Agent pane 布局、实时进度视图、阻塞告警提示和会话观察面板，帮助用户快速定位当前卡点。
11. **extension**：后续开放新的执行器、角色模板、通知插件与外部系统集成，但必须建立在前面 YAML 协议和文件协议稳定之后。

### 14.2 推荐落地顺序

1. **config**：先把 YAML DSL、每个 agent 的可配提示词/约束、只读产物规则和 `yaml-rules.md` 做实；没有这层，后面的自动化都没有统一输入协议。
2. **session**：先把 `.octopus/` 目录、session_id、会话文件骨架、角色会话代际和 `global_progress.md` / `blockers.md` 放下，后续所有模块才能围绕同一事实源工作。
3. **event-bus**：先把事件先落盘、再推进状态的 WAL 机制做实，并补上 `interrupt-all`、阻塞、重置、只读冲突等事件类型，保证整个自动化链路天然可追溯。
4. **orchestrator**：在配置和状态协议稳定后，先实现 Master 主循环：读人工输入、汇总进度、编排 A/B/C、检测死循环并自动收口。
5. **role-runtime**：补齐子 Agent 的被动触发、自举读 Markdown、会话重置、安全边界打断与只读拦截，形成“Master 调度 -> 子 Agent 执行 -> Master 收口”的闭环。
6. **artifact**：接着实现产物索引、版本与只读锁，尤其先把方案文档、审核意见、E2E 套件和执行报告的血缘做稳，不然后面的自动修复会失控。
7. **human-gate**：再把人工介入协议接进来，确保 `inject` / `approval` / `interrupt-all` 真正进入主流程，而不是变成旁路备注。
8. **cli**：此时补齐稳定命令行为最合适，把 `run` / `validate` / `reset-session` / `interrupt-all` / `report` 全部映射到前面已经稳定的协议层。
9. **recovery**：恢复能力依赖真实的事件、状态、角色代际、产物锁与回合文件，放在主链路稳定后实现更可靠。
10. **tmux**：等主流程和恢复链路可跑后再做可视化编排，能避免在不稳定协议上反复调整 pane 设计。
11. **extension**：插件和模板属于放大器，不是首版生存能力，最后做可以避免过早抽象。

### 14.3 排序原因

- 前 5 步优先构建“YAML 可描述 -> 文件可落盘 -> Master 可调度 -> 子 Agent 可执行”的最小自动化主链路。
- 第 6 到 8 步补齐产物锁、人机介入和 CLI 入口，让 `A 设计 -> B 审核 -> A 重置实现 -> B 审核差异 -> C 产出 E2E -> A 执行修复` 这条理想闭环真正能跑起来。
- 第 9 到 10 步再补恢复和可视化，保证系统在卡死、重启、阻塞和人工介入后仍然能解释“现在卡在哪、下一步该怎么走”。
- 第 11 步最后开放扩展点，保持首版实现简洁，符合“先把核心跑通，再放大生态”的原则。
